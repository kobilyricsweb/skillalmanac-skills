# code-risky-pattern-scan

## One line

Read-only first pass over a code folder that flags nine risky patterns, ranks each hit by severity, file and line, and shows every secret-like value masked.

## What it does

The skill runs a small Python script over one folder of source files. The script walks the folder without following symbolic links, skips dependency and build directories such as node_modules and dist, and reads only files with common source or configuration extensions. Each line of each file is tested against nine regular expressions. The patterns cover dynamic evaluation (eval and exec calls), subprocess calls that pass shell=True, SQL statements assembled by string concatenation or formatting, AWS-shaped access key identifiers, assignments of password-like or token-like names to quoted values, private key headers, disabled TLS certificate checks, pickle or dill loads, and md5 or sha1 hashing.

Every match becomes one finding with a severity, a pattern identifier, a relative file path, a line number and a short snippet. Secret-like values longer than four characters keep only their first two characters followed by asterisks, and shorter ones are fully starred, so the report never shows a credential in full. Findings are sorted high before medium before low, then by pattern identifier, file and line. The script prints one JSON object and exits 0, 1 or 2.

The skill then turns that JSON into a report with a coverage summary, a ranked table, next steps and a disclaimer. The disclaimer states that the output is pattern matching for first-pass review and not a vulnerability assessment.

## When to use

Use it when a reviewer wants a quick list of places to look before a deeper review, when a folder of older code has never been checked for these specific patterns, or when a team asks for a rough scan before a release. It is useful for triage because each finding names an exact file and line.

## When not to use

Do not use it as a security audit, a penetration test, a compliance check, or a statement that code is safe. It does not analyze data flow, so it cannot tell whether an eval call receives user input. It does not check dependencies, known vulnerabilities, configuration of running systems, or binaries. It does not fetch repositories; the code must already be on disk as text.

## Requirements

Python 3.9 or later, using only the standard library. No network access, no installed packages and no write access to the scanned folder are needed. The script never writes files. A folder of up to 5000 candidate files is read, and any single file above 2 MB is skipped and counted.

## Limits

The scanner matches text. It does not parse code, so a commented-out line or a string that merely contains the word eval is still reported. Quoted SQL that itself contains single quotes can slip past the SQL pattern. Secret detection depends on shape and on variable names, so a real key in an unusual format or a password held in a variable with another name will be missed, and a placeholder that happens to look like a key will be reported. Lines longer than 4000 characters are cut before matching. The severity values are working values chosen by the author, not a published standard. The scanner does not verify whether any secret is live, whether any input is attacker-controlled, or whether any TLS setting is reachable in production.
