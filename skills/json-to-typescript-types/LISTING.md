# JSON to TypeScript types

## One line

Infers exported TypeScript interfaces from a JSON sample and lists the fields that need a human check.

## What it does

The skill runs a standard-library Python script over one JSON file. The file must hold a single object, or a non-empty array whose items are all objects. The script walks every item and records the kind of value found at each key path: string, number, boolean, null, object or array. It then writes one exported interface per object position. Property names come from the JSON keys, and interface names are PascalCase versions of those keys. A key that is missing from any item becomes optional. A key that is null in some items and typed in others becomes a union with null.

Where the sample cannot settle a type, the script still writes a best guess and records a finding. A field that is null in every item is typed as null. An array that is empty in every item is typed as unknown[]. A position that mixes two non-null kinds becomes a union and is flagged. Two different paths that produce the same interface name get a numeric suffix and are flagged.

The output file is new. The script opens it in exclusive-create mode and exits with code 2 if the path exists, so an earlier draft is never overwritten.

## When to use

Use it when you have a real response from an API or a config file and need a first-pass TypeScript type in minutes. It fits a sample with five or more records, where optional keys are likely to show up in some of them. It also fits a review step: the findings list tells you which types came from guesses rather than from values.

## When not to use

Do not use it on a single record and treat the optional markers as facts. With one item every key is required, which is a property of the sample and not of the API. Do not use it to generate runtime validators, JSON Schema or code that checks incoming data. It writes only types. Do not use it on data you have not checked against the live source, because the output reflects the sample and nothing more.

## Requirements

Python 3.9 or later, standard library only. No network, no subprocess, no third-party packages. The input file must be UTF-8 JSON of at most 2 MB. The output name must end in .ts and must not exist.

## Example

Input: `fixtures/sample_records.json`, a five-item array with a nullable field, an optional field, an always-null field, an always-empty array and a nested object. Command and output:

```
python -I scripts/json_to_ts.py fixtures/sample_records.json out.ts
```

Summary line on stdout, exit code 1:

```
{"status": "findings", "interfaces": 2, "optional_properties": 2, "findings": [{"code": "NULL_ONLY", "path": "$.deleted_at"}, {"code": "EMPTY_ARRAY", "path": "$.labels"}, {"code": "MIXED_TYPES", "path": "$.score"}]}
```

Contents of `out.ts`:

```
// Generated by json_to_ts.py from a JSON sample. Check every finding and every optional marker against the live source before use.

export interface Root {
  id: number;
  name: string;
  email: string | null;
  address: Address;
  nickname?: string | null;
  deleted_at: null;
  labels: unknown[];
  score?: string | number;
}

export interface Address {
  city: string;
  zip: string;
}

export type RootList = Root[];
```

## Limits

The script reads the sample and nothing else. It does not check the sample against the live API, against documentation or against any schema, so a field that looks stable in five records may vary in production. Optional markers are only as reliable as the sample size. Singularization is a suffix rule, not a dictionary, so some plural names produce odd interface names; check them by hand. Non-ASCII keys are dropped from interface names and fall back to a generic name with a numeric suffix. The script does not verify that the emitted TypeScript compiles in a project, does not check the sample's provenance, and does not judge whether a union is intended. It writes no data values into its output or summary.
